一、痛点分析(7 大痛点)

🔴 背景:行业现状

传统金融业务中(银行理财、保险、基金)由于监管要求,所有销售过程必须进行"双录"(销售+客户双方同时录音录像)。

当前行业普遍存在"线上线下割裂"的痛点,导致合规风险、客户体验差、运营成本高。

痛点 1:线上线下话术不同步 ⚠️

现象:同一款产品在营业网点和手机 APP 上的话术不一样。线下客户得到的信息和线上客户不一致,产生误解、投诉。

原因:线下由客户经理人工引导,话术存于大脑/纸质;线上话术由 IT 硬编码到 APP 流程里,两边各自维护。

后果:

  • 同一客户线下咨询、线上购买时,信息不一致,产生信任危机
  • 监管检查发现两个版本话术,直接处罚
  • 产品更新时需要改两套话术,容易遗漏

痛点 2:线下双录视频合规性难以保证 ⚠️

现象:线下双录的录像存在客户经理本地电脑或 USB 设备中,后期可能被剪辑、替换、删除,留下合规隐患。

原因:营业网点分散,缺乏统一存储;视频文件大,无法实时上传;录像设备五花八门。

后果:

  • 发生纠纷时,视频证据缺失或被质疑完整性
  • 监管要求"双录资料至少保存 15 年",实际难以满足
  • 无法证明"销售当时已完整披露风险"

痛点 3:质检结果线上线下一致性差 ⚠️

现象:线下双录靠人工抽检(2-3%覆盖率),线上全量 AI 质检。同一句话术、同一句话,质检结果可能不同。

原因:线下缺乏智能质检工具,只能事后回听;线上 AI 模型未覆盖全量关键词。

后果:

  • 客户经理对质检规则理解不一致,执行标准不一
  • 违规销售在线下不易被发现,留下诉讼风险
  • 质检数据无法统一分析,无法定位系统性问题

痛点 4:流程数据原子性和一致性难保证 ⚠️

现象:创建订单→扣库存→扣款→发送通知 这一连串操作,如果中间任何一步失败,数据可能错乱(订单已创建但库存未扣 / 钱已扣但订单未生成)。

原因:传统单体事务(@Transactional)无法跨服务/跨库;微服务化后需要分布式事务,但 XA 性能差且对业务侵入大。

后果:

  • 对账不平,客户投诉
  • 需要人工修复数据,运营成本高
  • 极端情况下,客户付了钱但产品没买到

痛点 5:话术模板按产品/风评分类管理混乱 ⚠️

现象:银行理财、基金、保险、信托 各自一套话术,R1-R5 风险等级又各有差异。客户经理要记几十套话术,容易搞混。

原因:话术分散在 Word/Excel/PPT 中,缺乏统一管理;没有按"产品+风险等级"的结构化组织。

后果:

  • 客户经理对 R4 客户误用 R2 话术,造成不当销售
  • 新员工培训成本高,上手慢
  • 话术版本无法追溯(谁改了、什么时候改的)

痛点 6:客户购买流程不顺畅 ⚠️

现象:客户从意向到完成购买,需要切换多个系统(APP 双录→网点签字→回 APP 看结果),流程断点多。

原因:线上线下系统割裂,数据不互通;每个环节都要客户重新认证身份。

后果:

  • 客户中途放弃(行业平均 30% 流失率)
  • 客户经理要在多个系统间切换操作,效率低
  • 客户身份核验多次,体验差

痛点 7:缺乏统一审计与司法证据 ⚠️

现象:发生纠纷时,无法提供完整证据链(谁卖了什么、说了什么、签了什么、钱去了哪)。

原因:各环节数据分散存储,日志不完整,无法还原全过程。

后果:

  • 诉讼时败诉风险高
  • 无法满足监管"全流程可回溯"要求

✅ 解决方案:线上线下双录融合系统(AIRecord)

本系统通过 统一话术引擎 + 统一流程编排 + 统一质检引擎 + 统一证据存证 四统一,彻底解决以上 7 大痛点。

六、数据一致性方案(Saga 分布式事务)

❓ 为什么需要 Saga?

购买流程涉及多步操作:

1. 创建订单 (dr_session 状态变更)
2. 扣减库存 (产品库存 -1)
3. 扣款 (账户余额 -amount)
4. 发送通知 (短信/邮件)

传统单体事务(@Transactional)无法跨库/跨服务,失败时必须人工对账。

本系统使用 Saga 分布式事务,失败自动逆序补偿,数据最终一致。

💻 业务方代码(零侵入)

@Service
public class OrderSagaExample {

    // ====== Saga 入口 ======
    @Saga(type = "ORDER_SUBMIT", sessionKey = "#dto.orderId", operator = "'system'")
    public String submitOrder(OrderDTO dto) {
        return "提交成功";
    }

    // ====== 步骤 1: 创建订单 ======
    @SagaStep(name = "CREATE_ORDER", order = 1,
              compensate = "compensateCreateOrder",
              retryable = true, maxRetries = 3)
    public void createOrder(OrderDTO dto) {
        // 业务逻辑 - REQUIRES_NEW 独立事务
        orderStorage.put(dto.getOrderId(), dto.getQuantity());
    }

    // 步骤 1 补偿 - 逆序调用
    public void compensateCreateOrder(OrderDTO dto) {
        orderStorage.remove(dto.getOrderId());
    }

    // ====== 步骤 2: 扣减库存 ======
    @SagaStep(name = "DEDUCT_STOCK", order = 2,
              compensate = "compensateDeductStock")
    public void deductStock(OrderDTO dto) {
        if (stock < dto.getQuantity()) {
            throw new RuntimeException("库存不足");
        }
        stockStorage.put(dto.getProductId(), stock - dto.getQuantity());
    }

    public void compensateDeductStock(OrderDTO dto) {
        stockStorage.put(dto.getProductId(), stock + dto.getQuantity());
    }

    // ... 步骤 3 扣款 / 步骤 4 通知 类似 ...
}

✅ 解决痛点 4 (数据原子性)

  • 声明式:业务方只写 @Saga / @SagaStep,框架处理事务
  • 自动补偿:任一失败,逆序自动调用 compensate 方法

  • 全审计:SagaLog 记录每步状态,可视化追踪
